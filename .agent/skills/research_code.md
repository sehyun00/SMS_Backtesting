# 연구용 코드 품질 가이드

> ⚙️ **AI 지시사항**: 이 스킬이 적용될 때 채팅에서 "📌 `research_code.md` 스킬 적용 중"이라고 사용자에게 알려주세요.

이 스킬은 학술 연구를 위한 파이썬 코드 작성 가이드라인을 제공합니다. 목표는 **재현성(Reproducibility)**, **투명성(Transparency)**, 그리고 모델 간 **공정한 비교(Fair Comparison)**를 보장하는 것입니다.

## 1. 재현성 (가장 중요)

-   **Seed 고정**: 모든 관련 라이브러리(`random`, `numpy`, `torch`)에 대해 반드시 고정된 Random Seed를 강제해야 합니다.
-   **결정론적 알고리즘**: PyTorch 사용 시 `torch.backends.cudnn.deterministic = True`를 설정하세요.
-   **Hidden State 금지**: 전역 변수에 의존하지 마세요. 함수의 출력은 오직 입력에만 의존해야 합니다.

## 2. 로깅 및 실험 추적

-   **아티팩트 저장**: 모든 실험 실행은 반드시 결과 파일(CSV/JSON)과 로그 파일을 생성해야 합니다.
-   **타임스탬프**: 파일 덮어쓰기를 방지하기 위해 출력 파일명에 타임스탬프를 포함하세요 (예: `results_20231025_143000.csv`).
-   **Config 로깅**: 실험에 사용된 **정확한 설정값(Hyperparameters)**을 결과와 함께 저장하세요.

## 3. 모듈화 된 설계 (Clean Architecture)

-   **관심사의 분리**:
    -   `preprocessing`: 데이터 변환만 수행. 모델 로직 포함 금지.
    -   `models`: 네트워크 구조만 정의. 데이터 로딩이나 학습 루프 포함 금지.
    -   `training`: 데이터와 모델을 조율하여 학습 실행.
-   **Config 기반 제어**: 하이퍼파라미터 하드코딩 금지 (예: `lr=0.001` 절대 금지). 설정 객체나 딕셔너리를 통해 주입하세요.
-   **표준 인터페이스**: 공정한 비교를 위해 모든 모델은 공통 메서드 시그니처(예: `train_step(batch)`, `predict(state)`)를 공유해야 합니다.

## 4. 코드 건전성 (Code Health)

-   **타입 힌트**: 모든 함수 시그니처에 파이썬 타입 힌트(`def func(x: int) -> float:`)를 사용하세요.
-   **Docstring**: 모든 public 함수/클래스는 입력, 출력, 목적을 설명하는 Docstring을 포함해야 합니다.
-   **매직 넘버 금지**: 의미 있는 이름을 가진 상수로 정의해서 사용하세요.

### 2. 연구 코드 표준 (Research Code Standards)
**목표**: 재현성(Reproducibility) 및 AI 협업을 위한 가독성 확보.

#### 규칙 1: 기능 동등성 우선 (Functional Parity First)
- **로직 단순화 금지**: "AI 최적화"는 코드의 *구조*(모듈화)를 개선하는 것이지, 복잡한 기능을 제거하는 것이 아닙니다.
- **복잡성 보존**: 원본 모델이 RL, Multi-head, 또는 특정 Loss 함수를 사용한다면, 반드시 그대로 보존해야 합니다.
- **최우선 중요사항**: 리팩토링된 코드는 동일한 입력에 대해 레거시 코드와 수학적으로 **동일한 결과**를 산출해야 합니다.

#### 규칙 2: 컨텍스트를 위한 모듈화 (200줄 제한)
- **파일 크기**: 가능한 한 파일 크기를 200줄 미만으로 유지하세요.
- **로직 분리**: 클래스(예: `Trainer` 또는 `Agent`)가 200줄을 초과하면 하위 컴포넌트로 분리하세요 (예: `agent/actor.py`, `agent/critic.py`, `agent/buffer.py`).
- **평탄한 구조**: 깊은 중첩(예: `models/hybrid/actor/encoders.py`)은 피하세요. 패키지 내에서 평탄한 모듈 구조(예: `models/hybrid/encoders.py`)를 선호하세요.
- **명확한 Import**: `__init__.py`를 사용하여 하위 모듈에서 더 깔끔한 API를 노출하세요.

## 5. 마이그레이션 규칙 (본 프로젝트 전용)
-   코드를 `new/`로 이관할 때, **절대 복사-붙여넣기 하지 마세요.**
-   위 표준을 준수하도록 **리팩토링하여 재작성**해야 합니다.
-   사용하지 않는 import 문과 죽은 코드는 제거하세요.

## 6. 버그 수정 원칙

-   **근본 원인 분석**: 증상만 고치지 말고, 왜 발생했는지 추적하세요. 예: "변수가 None이다" → "왜 None인가?"
-   **최소 변경**: 버그와 무관한 코드는 건드리지 마세요. 리팩토링은 별도 커밋으로 분리하세요.
-   **회귀 방지**: 수정 후 관련 테스트가 있는지 확인하고, 없으면 추가하세요.
-   **커밋 메시지 명확화**: 버그 수정 시 원인과 해결 방법을 커밋 메시지에 기록하세요.
    -   예: `fix(backtester): target_head 인자가 TGNN forward에 전달되지 않던 문제 수정`
-   **디버그 코드 정리**: `print()` 문이나 임시 로그는 반드시 수정 완료 후 제거하세요.

## 7. 문서화 원칙

-   **README 업데이트 조건**: 다음 경우에만 README를 업데이트하세요:
    -   새 모듈/기능 추가
    -   기존 인터페이스(API, CLI 인자 등) 변경
    -   실행 방법 변경
-   **버그 수정 시**: 사용자 인터페이스가 변경되지 않으면 README 업데이트 불필요
-   **주석 우선**: 코드 내부 변경은 코드 주석으로 문서화
-   **README 길이**: 문서 파일은 200줄 제한 적용 안 됨. 충분히 상세하게 작성하세요.
